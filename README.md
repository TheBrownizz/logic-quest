# Logic Quest

Logic Quest הוא משחק לימוד בעברית (ממשק מימין לשמאל) שמלמד לוגיקה דיגיטלית ומיתוג דרך חדרי חידות, שערים לוגיים ומפת עולם. השחקן מתקדם בין שלבים, פותר חדרים עם טענות נכונות ושקריות ומקבל משוב על הנימוק שלו.

## הרצה מקומית

```bash
npm install
npm run dev
```

## בדיקות

```bash
npm test        # בדיקות יחידה ותוכן (Vitest)
npm run e2e     # בדיקות קצה-לקצה (Playwright)
```

Playwright בונה את האפליקציה ומריץ שרת `vite preview` משלו (`reuseExistingServer: false`) על הפורט שבמשתנה `E2E_PORT` (ברירת המחדל 4173, עם `--strictPort`). כשכמה עותקים של הריפו מריצים e2e באותו זמן, לכל אחד פורט משלו: `E2E_PORT=4182 npm run e2e`.

בדיקות ה-e2e לא רצות ב-CI: הדפדפנים של Playwright לא מותקנים שם, והתקנתם איטית. הריצו אותן מקומית לפני דחיפה.

## הוספת תוכן

התוכן נמצא בתיקייה `src/content/switching/`. אחרי כל שינוי, הוולידטור ובדיקות התוכן חייבים לעבור (`npm test`).

כללים:

- שדה `compute` חובה בחדרי מספרים.
- לפחות 40% מהטענות שקריות.
- הנימוקים לא מצהירים על פסק הדין (נכון/לא נכון).
- שמות הכניסות והיציאות (IN/OUT) מסודרים לפי סדר אלף-בית.
- לשער יש לכל היותר 2 כניסות.
- המקור הוא `סילבוס: <נושא>`.
- הטקסט מקורי, לא מועתק.
- כל נוסחה בתוך טקסט עברי עטופה ב-`ltr()` מ-`helpers.ts` (למשל `` `פתרו ${ltr('30 = 3r + 6')}.` ``). העזר מוסיף תווי בידוד LTR (U+2066…U+2069) והופך רווחים לרווחים לא-שבירים, כך שהנוסחה נקראת משמאל לימין ולא נשברת בין שורות. זה חל על משוואות, ביטויים, אי-שוויונות, מחרוזות ביטים עם אופרטור, סימון כמו `(36)_r` או `Σ(...)` ומספרים שליליים. מספרים בודדים ומילים באנגלית (NAND, MUX) לא צריכים עטיפה. הבדיקה `formulas in Hebrew text are LTR-isolated` נכשלת על נוסחה לא עטופה.
- הממשק מציג טקסט תוכן דרך `Prose` (`src/ui/Prose.tsx`): טקסט עם עברית מוצג ב-`dir="rtl"`, וטקסט בלי עברית (נוסחה בלבד) ב-`dir="ltr"`. לא משתמשים ב-`dir="auto"`. בהגדרת קוד (`definition`) כל שורה (מופרדת ב-`\n`) היא בלוק נפרד עם כיוון משלה.

## שיעורים

לפני החדרים של כל שלב יש שיעורים אינטראקטיביים (מסמך העיצוב: `docs/superpowers/specs/2026-11-27-lessons-design.md`). שיעור הוא תוכן, לא קוד: רשימת צעדים מסוגים קבועים, שנגן אחד (`src/ui/lessons/LessonScreen.tsx`) מציג.

איפה מה:

- הטיפוסים: `src/content/lessons/types.ts` (`Lesson`, `Step`, `SkipQuestion`, `WidgetName`).
- השיעורים של כל שלב: `src/content/switching/lessons/stageN.ts`, שמייצא `lessons: Lesson[]` ו-`figures` (איורי SVG לפי מזהה). הקובץ `index.ts` אוסף את כולם.
- הוולידטור: `validateLessons(world, lessons)` ב-`src/content/lessons/validate.ts`. כל שלב בודק את השיעורים שלו ב-`tests/content/lessons-stageN.test.ts` בעזרת `expectLessonsValid(stageId)` מ-`tests/content/lessonTestUtils.ts`.
- וידג'טים: `src/ui/lessons/widgets/<Name>.tsx` (רכיב) ו-`<name>Logic.ts` (`initial`, `isGoalMet` טהורים). הרישום ב-`registry.ts` קבוע: מחליפים רק את שני הקבצים של הווידג'ט.
- הטיפוסים של כל וידג'ט (`<Name>Config`, `<Name>State`, `<Name>Goal`) מוגדרים ב-`<name>Logic.ts` והם חוזה: מי שמממש וידג'ט לא משנה אותם. `registry.ts` מוקלד לפי המפה `WidgetTypes` (`src/content/lessons/widgetTypes.ts`), ולכן מימוש שסוטה מהם לא מתקמפל.
- צעד וידג'ט בקובץ שיעור נכתב תמיד דרך `widgetStep(...)` מ-`src/content/lessons/widgetTypes.ts`, שבודק בזמן קומפילציה את `config`, `goal` ו-`example` מול הטיפוסים של הווידג'ט: `` widgetStep({ id: 'dial', widget: 'BaseDial', prompt: '…', config: { base: 2, width: 4 }, goal: { value: 5 }, example: { digits: [0, 1, 0, 1] } }) ``.
- רכיב וידג'ט מקבל `config`, `goal`, `onState`, `completed` ו-`reducedMotion`. קוראים ל-`onState` רק מתוך effect או מטפל אירוע, אף פעם לא בזמן render, כי היא יכולה להשלים את הצעד. כש-`completed` אמת (חזרו לצעד שכבר הושלם), וידג'ט עם מטרה יכול להציג את המצב הסופי.
- ב-`config` יש רק תוויות קצרות, כמו שמות משתנים או נוסחה, בלי עברית ועד 40 תווים. משפט שהשחקן קורא שייך ל-`prompt`. כל מחרוזת ב-`config` עוברת גם היא את ה-lint.
- מזהי איורים (`figures`) גלובליים: מוסיפים להם קידומת של השלב (`s2-...`). מזהה שמופיע בשני קבצים נכשל בבדיקה.
- הכללים של פתיחת החדרים, מבחן הדילוג והשמירה: `src/game/lessonRules.ts`.

סוגי הצעדים, ומתי "המשך" נפתח:

- `explain`: טקסט קצר, עד כ-60 מילים (מעל 70 זו שגיאה), ואופציונלית `figure` (מזהה במפת `figures` של קובץ השלב, שמתחיל ב-`<svg`). נפתח מיד.
- `widget`: וידג'ט עם הוראה. בלי `goal` נפתח מיד. עם `goal` חובה גם `example`, מצב שמקיים את המטרה. הוולידטור בודק ש-`isGoalMet(example, goal, config)` מתקיים, ושהמצב ההתחלתי לא מקיים אותה כבר.
- `check`: 2–4 תשובות שונות, תשובה נכונה אחת (`correct`), ו-`feedback` לכל תשובה (באותו אורך). המשוב לתשובה שגויה מסביר את הטעות הספציפית. בטעות מנסים שוב בלי עונש.
- `check-number`: `answer` ו-`compute()` שמחזירה אותה (משווים בלי רווחים ובלי הבדלי אותיות), ו-`feedbackWrong`.
- `try`: מיני-מעבדה עם `LabPuzzle` ו-`hints`, ובודקים של החדרים. אין כוכבים, `helped` או טיוטות. במעגל אין רכיבים (chips): הפלטה היא בדיוק `allowed`, ואסור `unlocksChip`.
- `recap`: 3–5 נקודות. זה תמיד הצעד האחרון והיחיד מסוגו, והוא מסך הסיום.

כללים נוספים: לא יותר משני `explain` ברצף. מזהי שיעורים ייחודיים, ומזהי צעדים ושאלות ייחודיים בתוך השיעור. ב-`skipQuiz` לפחות 6 שאלות (המבחן מגריל 4 ונעצר בטעות הראשונה). `source` הוא `סילבוס: <נושא>`. כל כללי ה-lint של הטקסט (`lintText` ב-`src/content/lint.ts`: נוסחאות, מספרים שליליים וקבוצות ביטים בתוך `ltr()`) חלים על כל מחרוזת בשיעור.

התקדמות: `SaveData.lessons[lessonId] = { stepId, done, skipped?, quizFailedAt? }`. נשמר מזהה הצעד, לא אינדקס, ולכן מותר לשנות שיעור. מזהה שנמחק מחזיר לתחילת השיעור. אל תשנו מזהה של שיעור קיים: שחקנים יאבדו את ההתקדמות בו. החדרים והריצה של שלב נפתחים כשכל השיעורים שלו הושלמו (הגיעו לסוף או עברו את מבחן הדילוג), או כשכבר נפתר בו חדר. ברגע שהשיעורים פותחים שלב, הוא נרשם ב-`SaveData.openStages` ונשאר פתוח, גם אם יתווספו לו שיעורים בהמשך. מבחן דילוג שנכשל לא מתחיל את השיעור: הסטטוס נשאר "חדש".

בבדיקות e2e: `unlockedSave()` ו-`withLessonsDone()` מ-`tests/e2e/helpers.ts` מסמנים את כל השיעורים כגמורים. `playLesson()` מ-`tests/e2e/lessonWalk.ts` עובר על שיעור לפי התוכן שלו. הפרמטר `?autofill=1` מסמן כמושלמים צעדי `widget` עם מטרה וצעדי `try` (כמו ה-autofill של החדרים), כדי שאפשר יהיה לעבור על כל שיעור בבדיקה.

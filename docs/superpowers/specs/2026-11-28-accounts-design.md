# מסמך עיצוב: חשבונות משתמש ושמירה בענן

תאריך: 28.11.2026 · הפרויקט הראשון מתוך `2026-11-28-rpg-vision.md`

## 1. הכוונה
היום ההתקדמות נשמרת רק בדפדפן: מחשב אחר מתחיל מאפס, וניקוי הדפדפן מוחק הכול. המשתמש רוצה **חשבון קבוע**: נכנסים עם Google, וכל ההתקדמות נשמרת בשרת ונגישה מכל מכשיר. זה גם התנאי לשכבת ה-RPG (XP, מטבעות, מגדל), ולמוצר שסטודנטים אחרים משתמשים בו.

**מדד הצלחה:** נכנסים עם Google במחשב, פותרים חדר, נכנסים בטלפון, וההתקדמות שם.

## 2. מטרות, לא־מטרות, אנטי־מטרות
**מטרות:**
- התחברות עם Google, והתנתקות.
- שמירת ה-`SaveData` הקיים, וכל מה שיתווסף אליו בעתיד, בשרת לכל משתמש.
- מעבר חלק: מי ששיחק בלי חשבון ונרשם לא מאבד כלום.
- המשחק ממשיך לעבוד בלי חשבון ("אורח") ובלי רשת.
- מחיקת חשבון, כולל כל הנתונים.

**לא־מטרות (כרגע):**
- טבלאות מובילים, חברים ושיתוף.
- התחברות באימייל וסיסמה.
- XP ומטבעות. הם שייכים לפרויקט 2, אבל ייכנסו לאותו מבנה שמירה בלי שינוי בשרת.
- גרסת ה-Artifact ב-claude.ai נשארת במצב אורח בלבד, כי חלון ההתחברות של Google לא נפתח שם.

**אנטי־מטרות:**
- איבוד התקדמות בגלל התנגשות בין מכשירים.
- דליפת נתונים של משתמש אחד למשתמש אחר.
- חובה להתחבר כדי לשחק.
- מפתח סודי בתוך הקוד של האתר.

## 3. אילוצים
- האתר נשאר סטטי ב-GitHub Pages, ואין שרת משלנו.
- **Supabase:** Postgres, ‏Auth ו-Row Level Security. בחינם בהתחלה.
- המפתח הציבורי (anon key) ב-Supabase גלוי בקוד מעצם הגדרתו, וההגנה היא חוקי RLS. ה-service key לעולם לא נכנס לאתר.
- האתר משתמש בניתוב hash (`#/...`). לכן ההתחברות משתמשת ב-**PKCE**, שמחזיר `?code=` ב-query string, ולא ב-implicit flow, שמחזיר טוקנים ב-hash ומתנגש עם הנתב.
- הבדיקות ב-CI רצות בלי רשת. ההתחברות האמיתית נבדקת ידנית.

## 4. גישות שנשקלו
| גישה | יתרונות | חסרונות |
|---|---|---|
| **Supabase** (נבחרה) | מערכת Postgres ו-Google Auth מוכנים, חינמי, עובד מאתר סטטי, ו-RLS מגן על הנתונים | תלות בשירות חיצוני |
| Firebase | פופולרי, Google Auth מובנה | מסד NoSQL, ונעילת ספק חזקה יותר |
| שרת משלנו (Node + DB) | שליטה מלאה | אחסון, תחזוקה ואבטחה עלינו |

## 5. העיצוב
### 5.1 נתונים בשרת
```sql
create table saves (
  user_id uuid primary key references auth.users on delete cascade,
  data jsonb not null,           -- SaveData כפי שהוא
  updated_at timestamptz not null default now()
);
alter table saves enable row level security;
create policy "own row" on saves for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
```
- שורה אחת לכל משתמש, עם כל ה-SaveData כ-JSON. אין טבלת פרופיל בשלב הזה: השם והתמונה מגיעים מ-Google.
- ה-SQL נשמר בריפו (`supabase/schema.sql`) עם הוראות הרצה.

### 5.2 שמירה: "קודם מקומי"
- המשחק ממשיך לקרוא ולכתוב ב-localStorage, כמו היום, ולכן הוא מהיר ועובד גם בלי רשת.
- אם יש משתמש מחובר, כל שינוי נשלח גם לשרת (upsert), אחרי השהיה של כ־2 שניות ממנו.
- בכשלון, למשל בלי רשת, מנסים שוב מאוחר יותר ומציגים סימן קטן "לא מסונכרן".
- נבנה `CloudProgressStore` שעוטף את `LocalProgressStore` הקיים, דרך אותו ממשק `ProgressStore`, כפי שתוכנן בגרסה 1.

### 5.3 מיזוג כשיש שתי גרסאות
בכניסה, ובכל טעינה, אם יש גם שמירה מקומית וגם שמירה בשרת, ממזגים אותן בפונקציה טהורה `mergeSaves(a, b)`. **מיזוג לעולם לא מאבד התקדמות:**

| שדה | כלל המיזוג |
|---|---|
| חדרים | לכל דגל ב-`rooms`, הטוב מבין השניים (OR) |
| `knowledge`, `flagged`, `openStages` | איחוד |
| `bestRun` | המקסימום |
| `lessons` | `done` = OR; `stepId` לפי השמירה המתקדמת יותר |
| `chips` | החיתוך עם פחות שערים |
| `drafts` | לפי `updated_at` של השמירה החדשה יותר |
| `helped` | איחוד, ליתר ביטחון |

בעתיד שכבת ה-RPG תוסיף שדות, ולכל שדה חדש חייב להיות כלל מיזוג. בדיקה תיכשל אם נוסף ל-SaveData שדה שאין לו כלל.

### 5.4 ממשק
- **בכותרת:** כפתור "התחברות עם Google". אחרי ההתחברות מוצגים התמונה, השם ותפריט עם "התנתקות" ו"מחיקת חשבון".
- **סימן סנכרון קטן:** ✓ מסונכרן, ⟳ שומר, ⚠ לא מסונכרן.
- **אורח:** אחרי שהאורח פותר 3 חדרים, מופיעה פעם אחת הודעה עדינה: "התחבר כדי לשמור את ההתקדמות בכל מכשיר". אפשר לסגור אותה, והיא לא חוזרת.
- **מחיקת חשבון:** מוחקים את השורה ב-`saves` ואת המשתמש, דרך Edge Function של Supabase שמשתמשת ב-service key בצד השרת, ואז מתנתקים. האתר עצמו לא מחזיק את המפתח.
- **התנתקות:** השמירה המקומית נשארת, אבל מסומנת כ"של אורח", כדי שמשתמש אחר באותו מחשב לא יקבל אותה בכניסה שלו.
- **דף פרטיות קצר:** מה נשמר (התקדמות, שם ואימייל מ-Google), איפה, ואיך מוחקים.

### 5.5 מה המשתמש צריך לעשות (חד־פעמי, עם הוראות צעד־אחר־צעד)
1. לפתוח פרויקט ב-Supabase.
2. ליצור OAuth Client ב-Google Cloud ולחבר אותו ל-Supabase.
3. להגדיר את כתובות ה-redirect: האתר ב-GitHub Pages, ו-localhost לפיתוח.
4. להריץ את `schema.sql`.
5. לתת ל-Claude את ה-Project URL ואת ה-anon key, שהם ציבוריים. הם יישמרו כ-GitHub Actions variables ויוזרקו בזמן build.

### 5.6 בדיקות
- **בדיקות יחידה** ל-`mergeSaves`: כל שדה, תכונת "לעולם לא מאבד", סימטריה, ו-idempotency.
- **בדיקות יחידה** ל-`CloudProgressStore` מול לקוח Supabase מזויף: השהיה, ניסיון חוזר וכשלון רשת.
- **e2e** עם לקוח מזויף, שמוזרק דרך דגל build של בדיקות: מצב אורח, התחברות מדומה, מיזוג, התנתקות ומחיקה.
- **בדיקה ידנית אחת של המשתמש** מול Google אמיתי: מחשב, ואז טלפון.
